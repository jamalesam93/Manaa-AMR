## 2024-05-15 - [Insecure LocalStorage Deserialization]
**Vulnerability:** Several utility functions (`getDailyChallenge`, `getDailyChallengeStats`) and the app context (`AppContext.jsx`) parse data from `localStorage` using `JSON.parse` without `try-catch` blocks or schema validation.
**Learning:** This exposes the application to DoS attacks through local storage injection. If the stored data becomes invalid JSON, the parsing throws an error that crashes the component or the whole application, leading to a persistent unhandled exception until `localStorage` is cleared manually.
**Prevention:** All data retrieved from `localStorage` must be parsed within `try-catch` blocks, strictly validated for expected types (e.g., `Array.isArray`, `typeof === 'object'`), and ensure `console.error` calls are restricted to development (`import.meta.env.DEV`).

## 2026-06-12 - [Insecure Deserialization in Trackers]
**Vulnerability:** Tracking functions (`streakTracker.js`, `progressTracker.js`, `achievements.js`) parse `localStorage` data using `JSON.parse` without verifying the type of the parsed data or falling back safely if missing attributes were returned. Furthermore, they log `error` to the console in production environments.
**Learning:** Returning unvalidated objects from `JSON.parse` can cause application instability when components expect specific object formats or array structures. Exposing the full stack trace to the console in production can leak sensitive internals or environment context.
**Prevention:** Data from `localStorage` should be safely parsed, validated using typeof or Array.isArray, and merged over default configurations (`{ ...defaultData, ...parsed }`) to avoid prototype pollution or state leakage. All `console.error` logs on catching parse errors should be wrapped in `if (import.meta.env.DEV)` blocks.
