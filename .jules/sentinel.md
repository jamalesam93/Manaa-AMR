## 2024-05-15 - [Insecure LocalStorage Deserialization]
**Vulnerability:** Several utility functions (`getDailyChallenge`, `getDailyChallengeStats`) and the app context (`AppContext.jsx`) parse data from `localStorage` using `JSON.parse` without `try-catch` blocks or schema validation.
**Learning:** This exposes the application to DoS attacks through local storage injection. If the stored data becomes invalid JSON, the parsing throws an error that crashes the component or the whole application, leading to a persistent unhandled exception until `localStorage` is cleared manually.
**Prevention:** All data retrieved from `localStorage` must be parsed within `try-catch` blocks, strictly validated for expected types (e.g., `Array.isArray`, `typeof === 'object'`), and ensure `console.error` calls are restricted to development (`import.meta.env.DEV`).
## 2024-05-28 - [Insecure Deserialization of localStorage data]
**Vulnerability:** Several utility files (`progressTracker.js`, `streakTracker.js`, `achievements.js`) were parsing JSON data from `localStorage` without validating the type of the resulting object (e.g. array vs non-array object). Error handling was also logging full errors via `console.error` in production.
**Learning:** `localStorage` is completely user-controllable. Simply checking if the parsed result is truthy is insufficient because it could be of an unexpected type (e.g. an array instead of an object, or an object instead of an array), potentially leading to runtime errors or unexpected behavior if the application attempts to use methods or properties specific to the expected type. Also, errors should be masked in production to avoid leaking info.
**Prevention:** Always strictly validate the type and structure of data parsed from `localStorage` using `typeof`, `Array.isArray`, and schema validation if necessary, before using it or combining it with defaults. Wrap debug logging in `import.meta.env.DEV` blocks.
